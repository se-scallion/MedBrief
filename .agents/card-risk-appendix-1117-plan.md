## A. 反向排雷（现状 → 新方案前提）

**R1 需求前提（"高危因素缺失"是否属实）——成立，有实证。**
- `lib/intakeCard.js:205-295` `buildSafetyBaseline()` 只做**"只提取、不推断"**：①基因标签 ②初诊基线（仅 WBC/LDH）③治疗安全基线 ④近期治疗节点；没有任何"高/中/低危"字段或判定。
- 模块①渲染 `lib/intakeCard.js:1399-1409` 就四格 + 基因 badge，无危险分层。
- 全库唯一"报警"口径是 `lib/cardPolicy.mjs:49-88` 的**危急值**（WBC<1 或>50、ANC<0.5、Hb<60、PLT<20 或>1000、FIB<1、Lac≥4、IL-6≥1000、PT≥20、APTT≥60、K<2.8/>6、NT-proBNP≥1800）——它是"单个值急诊报警"，**不是"中低高危分层"**：只覆盖 11 个 code，不含分期/基因/缓解状态/年龄/治疗反应。
- 复跑：`grep -n '高危\|中危\|低危\|危险分层\|risk' lib/intakeCard.js lib/cardPolicy.mjs` → 高危只在注释/基因标签名里出现，**无判定函数**。用户说的"缺失"属实。

**R2 库里到底有没有分层所需数据——有，但分散、填充率低。**
- 报告库 98 份；`clinicalDiagnosis` 填充 **2/98**，且值都是 `AL?`（`node /tmp/probe-risk2.mjs` 实测，脚本一次性只读，未落盘）。诊断全文在**病友档案** `data/intake/patient.json`：`diagnosis="急性B淋巴细胞白血病（Common-B-ALL可能）"`、`subtype=""`、`stage=""`（空）。
- 分层关键数据确实在库里：融合基因报告（7 份）含 `BCR::ABL1 P190/P210/P230`；骨髓形态学 2026-09-30 text 含「考虑 ALL-CR，请结合MRD及病史」；流式免疫分型 2026-09-30 是"治疗后微小残留病检测"；`FCM_MRD_PCT` 有异常细胞占比；染色体核型 2 份。
- 但 `stage`（分期）、`subtype`（分型）在档案里是**空的**，`clinicalContext` 的 `lastChemo/recentTxOrGcsf/marrowSummary` 也是空的。⇒ 若分层规则依赖这些字段，会大面积"未录入"，无法给医生判断。

**R3 我可能犯的错：把"我想显示"当"库里有"。** 必须逐字段区分三态：①库里有值且可信（如 BCR::ABL1 阳性）②库里有字段但值为空（stage/subtype/临床诊断）③库里根本没有该字段（如"危险度分组"原始文本、`Ph+` 的明确阴阳性判定除融合基因报告外无结构化字段）。**只有①能自动判定，②③必须显示"未录入/待核"，绝不能推断填值**（沿用"只提取、不推断"红线）。

**R4 真值来源分级（R8）——高危标线从哪来，是本次最大雷。** 现有 `CRITICAL_RULES` 是 2026-11-13 用户定稿《问诊卡逻辑 v3》里的默认阈值，可当"已有合同"；但**中/低/高危分层标线目前项目里没有任何权威来源**。不得由我、也不得由审核 AI 凭医学常识"编一套标线"当标准：医生判断所需的分层（如 ALL 的 Ph+/BCR-ABL、MRD 时点、年龄、初诊 WBC、免疫分型、巩固治疗反应）属于**临床指南内容**，AI 产出只能当"待医生确认的候选清单"，不能当"判定标准"写进代码。⇒ 本方案把"标线"分成两层：**可自动判定层**（库里有结构化值且来源明确，如 Ph+/BCR::ABL1 阳性、危急值命中、MRD 阳性）+ **展示待判层**（把原始值与出处摆到模块①，标线文字注明"待医生结合指南判断"，不写结论）。

**R5 语义裂缝（"高危基因"≠"高危疾病"）。** 模块①现有格名"分子与高危基因"里的"高危"指**基因标签**（`DISEASE_TAG_PATTERNS` 里 BCR::ABL1/TP53/KMT2A/IKZF1），与用户说的"中低高危整体分层"不是一回事。若直接在这格加"高危"结论，医生可能误读成"基因高危=整体高危"。必须在规格里区分。

**R6 过度设计 / 现成等价物。** `criticalOf()` 已在卡片P0区标"危急"；`buildSafetyBaseline()` 已有基因标签、初诊基线、安全基线。真正缺的是"把这些散点在模块①**汇总成可判断的视图**"，而不是新建一套分层引擎。⇒ 倾向"重排+补缺字段"，不重写判定层。

**R7 B 线需求前提——成立。** 打印件固定 3 页（`server.mjs:1514-1545` 返回整段 `card.html`；`CardPreview.jsx:49` `document.write(card.html)`，弹窗标题写死"打印预览（3 页 A4）"）。报告原件是逐份对象（`lib/reportStore.mjs` / `readReports()` + `/api/intake/blob/...`），具备"按 id 附页"的数据基础。

## B. 正向排雷（新方案 → 现有消费方）

**F1 破坏性动作。** A 线若补档案字段（stage/subtype），必须走病人档案 patch 接口、带审计、真库零直写。本方案草稿阶段**不改任何数据**。B 线附页只读取原件渲染，不改报告库。

**F2 连带副作用。** 改 `buildSafetyBaseline()` 返回形状 → `renderHtml()` 多处消费（`sb.baseline/safety/treatment/geneTags`），必须保持旧字段不删、只增；`card.json`（工作台 `trendAll/timeline` 等）也由 `buildCard` 产出，新增字段不能破坏 `verify-workbench.mjs` 契约。

**F3 键一致性。** B 线按 report id 附页，id 是查重/溯源键，**不许因附页改名或改 id**。

**F4 呈现层误报。** 若把"危急值命中"直接渲染成"高危结论"，可能把一次化疗后低谷（如 WBC 0.04）误读成疾病高危。分层视图必须带**日期与出处**，且区分"当前危急（单次事件）"与"长期危险分层（跨报告综合）"。

**F5 测试污染现场。** 两条线验证都用副本库 + 独立端口（5193–5199），真库零写入；本方案未跑任何写测试。

**F6 调用面。** B 线改 `/api/intake/card` 返回形状（如由纯 `html` 变成带附页的 `html`）→ 保留旧调用：`CardPage.jsx:119` 取 `card.html`、`CardPreview.jsx` 用 `card.html`，新增参数（如 `?append=id1,id2`）必须可选，默认行为零变化。

**F7 部署态。** 两线都改 `lib/**`/`server.mjs` → 执行者必须自己重启 5174 并自验 `head == git rev-parse --short HEAD`，不丢给用户。

**F8 治理资产。** A 线改 `cardPolicy.mjs` 属"改临床判断" → 必须同步 `tests/verify-card.mjs`；改模块①版面 → 必须出 UI 规格并挂 `test:card-layout` 同批复跑。B 线改打印契约 → `CardPreview.jsx` 的"3 页"文案、`docs/问诊卡逻辑.md` 的页数断言同步。

**F9 并发写冲突。** `.agents/outsourcing-log.md` / `testing-lessons.md` / `lib/reportStore.mjs` 注释属他人在途，本方案不认领、不改。

## D. 简化后的方案（只列留下的项）

**A 线（待审核澄清标线后细化）：**
1. 模块①顶部增一个"危险分层判断所需数据"视图：汇总**已存在**的 ①分子/高危基因标签（阳性优先）②危急值命中项（带日期与数值）③初诊基线（WBC/LDH，全量首/峰/末）④病友档案的诊断/分期/分型（空则写"未录入"）。**只摆原始值与出处，不写"高危/中危/低危"结论**——结论由医生结合指南判断（R4）。
2. 审核 AI 产出一份**候选标线清单**：逐条写"什么数据 + 什么阈值/状态 + 指向高危/中/低危 + 证据来源（项目已有规则 / 指南待医生确认）"，并明确哪些库里有、哪些库里没有。该清单交用户/医生确认前，**不进代码判定**。
3. 缺口数据（stage/subtype/临床诊断等）只做"未录入"显式提示，不自动填值（R3）。

**B 线：**
4. `/api/intake/card` 增**可选** `?append=<id,id>` 参数；默认无参数时输出与今天逐字相同（3 页）。附页按 id 读取原件 blob，原样附在 3 页之后，不改报告内容。
5. 卡片页加勾选 UI（"附哪些报告"），版面由 **UI 设计师出数值规格**后才编码；弹窗页数文案随附页数量动态显示，不再写死"3 页"。

**需要 AI 审核回答的核心问题（写进 review-input）：**
- Q1 高/中/低危分别需要哪些**结构化数据**？库里现有 98 份报告 + 病友档案哪些字段能支撑，哪些缺？
- Q2 每条标线的**判据**是什么（值/阈值/状态组合）？哪些能自动判、哪些必须交医生？
- Q3 按 R4，AI 不得自创标线当标准——审核者必须明确每条标线是"项目已有合同"还是"待医生确认的候选"。
- Q4 模块①应展示哪些数据项才能让医生**仅看顶部**就判断？逐项名 + 出处。
- Q5 B 线附页是否有我漏掉的雷（打印契约、 blob 权限、账号 owner 隔离）？

**无法自解的前提（需用户/医生拍板，审核不改）：**
- 中/低/高危的**医学标线本身**必须由医生确认；AI 与我都不给"标准"只给"候选"。
- 库里 stage/subtype/诊断大量为空，要不要补录由用户定。

**回退与门禁（G7）：** 两线都保留旧行为为默认（无 append 参数、模块①旧四格保留只增不删）；验收命令 `node tests/verify-card.mjs`、`npm run test:card-layout`、副本库端口验打印；真库零写入。
