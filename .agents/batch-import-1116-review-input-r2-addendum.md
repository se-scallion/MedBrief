## 二、规格侧两处缺口（需要 r2 或规格 v1.1 裁）

### 缺口 1：规格 §7 的"导入时"只写了**对库**一路，缺 r1 P0-1 要求的**批内**一路
- 规格 §7 判据写的是 `sha256(文件字节) === reports[].sha256`（对库），命中呈现 `Tag「同一文件已导入过」`。
- 但 r1 P0-1 的要害是**同批内重复**（同一张图拖一次再粘一次），此时**库里还没有它**，对库比对必然判"不重复" ⇒ 规格照做会**原样复现** r1 的 P0。
- v0.3 在 D-1 补了 5.2b/5.3b：批内命中 ⇒ **不新增第二张卡** + `message.warning('这张图本次已选过，已跳过')`；对库命中 ⇒ 建卡 + 打 Tag + `predup:{kind:'exact-file'}`。
- 请判：**两条路径的呈现不一致（批内跳过 / 对库建卡）**是否成立（必攻击点见 §三-1）。

### 缺口 2：规格 §7 末段写「算不了哈希 → 灰 Tag 本次未做文件查重（取计划建议 a）」，与 r1 P0-2 冲突
- 规格选 (a)：手机端（非安全上下文）不做预检、灰 Tag 明示。
- r1 P0-2 判：这正是"主场端等于没做"，要求 (d) 纯 JS SHA-256。
- **v0.3 定为 (d) 为主**：`crypto.subtle` 可用则用（快），否则纯 JS（~40 行、零依赖）；灰 Tag 只作**哈希抛异常**时的兜底。B4 用 `sha256Hex('abc') === ba7816bf…` 与 node `crypto` 对拍。
- 请判：① 这个裁定是否需要规格出 v1.1 同步（我认为需要，否则实现方照规格会做成 (a)）；② 纯 JS 实现是否要加"只对 ≤8MB 文件算，超限则灰 Tag"的成本护栏。

## 三、本轮必攻击点（在 r2 的 8 条之外新增 4 条）

1. **批内跳过 vs 对库建卡的不对称**是否合理？还是应统一为"都建卡并打 Tag，由用户决定"？
2. **v0.3 的 C-9 措辞**：徽标与上限 4 先实现，但 `拼接` 在 N>2 时**禁用** + `title="本次最多拼 2 张（多张拼接待实测放行）"`。这样是否已消除 r2 输入必攻击点 4 的自相矛盾？
3. **规格 A1 依赖 sticky 的"文档流占位"**：A1 断言里有 `最后一张卡.rect.bottom <= bar.rect.top + 0.5`。sticky 元素在**未贴底时**（短列表）会排在内容之后 ⇒ 该断言在短列表下仍成立吗？若短列表不吸底（缺口 3 的 D-3 第 5 条），A1 是否要分成"长列表贴底"与"短列表不吸底"两条判据？
4. **"更多"0 选不渲染后，C-13 的"清空勾选进更多"在 0 选时无处可达** —— 但 0 选时清空本无意义，是否还需一条断言防"选择态下「更多」忘记渲染"（即选 1/≥2 时必须有）？
