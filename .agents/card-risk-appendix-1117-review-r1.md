## 1. P0 逐条展开

### P0-1 R2 的数据事实错（最要紧：它会让"缺失"复现）

计划 R2 `:34` 写：「流式免疫分型 2026-09-30 是"治疗后微小残留病检测"；`FCM_MRD_PCT` 有异常细胞占比」。实测（只读）：

```bash
node -e "…对 98 份逐行扫 code 属于 (MRD|FCM_MRD_PCT|FCM_CD34_PCT|BM_BLAST_PCT)…"
# 只会打印两行，都是 2026-07-17 那份：
#   2026-07-17 流式免疫分型 | 异常细胞占有核细胞比例 code=FCM_MRD_PCT value=85.76
#   2026-07-17 流式免疫分型 | CD34+细胞占有核细胞比例 code=FCM_CD34_PCT value=84.42
```

而 **2026-09-30 那份"治疗后微小残留病检测"`rows = 0`**（内容全在 `text` 里，开头是"…治疗后微小残留病检测流式报告… 检测抗体：10个CD…"）。⇒ **MRD 的结构化值是空的**。模块①若按"取 `FCM_MRD_PCT`"实现，医生看到的会是"未录入"，而报告库里明明有这份 MRD——**这就是用户说的"高危因素显示有缺失"的同一个病**。

融合基因同样要对齐：7 份里 **只有 2 份有 rows**——

| 日期 | rows | 结构化内容 |
|---|---|---|
| 2026-07-18 | 5 | `BCR::ABL1（P190型）= 阳性(status=positive)`、P210 阴性、P230 阴性 |
| 2026-09-29 | 3 | `BCR-ABL P190 = 0`、`ABL = 395707`、**`BCR-ABL P190/ABL = 0%`**（RQ-PCR） |
| 07-19 / 07-22 / 07-24 / 09-30×2 | **0** | 仅 text（279 B / 804 B / 2257 B / 3485 B / 31474 B） |

**第三条最强证据被漏了**：`2026-07-15` 染色体核型 `text` 里有「9p-、**t(9;22)**、15q+、16q+；13 个正常核型」＋结果解释"t(9;22)(q34;q11.2)易位形成 BCR::ABL 融合基因"——**这是 Ph+ 在细胞遗传学层面的独立证据**，但 `rows=0`（无结构化行），模块①现在只靠 07-18 的标签，看不到它。

⇒ **R2 必须按上表重写**，并明确"模块①的 MRD 与核型两块，本版只能显示『原文在 2026-09-30 流式 / 2026-07-15 核型报告（点开看原件）』，不得凭空补值"。

### P0-2 A2 的机制不成立

`lib/cardPolicy.mjs:95-104`：

```js
export const REQUIRED_BASICS = [
  { code: 'WBC', … }, { code: 'Hb', … }, { code: 'PLT', … }, { code: 'NEUT_ABS', … },
  { code: 'PT',  … }, { code: 'APTT', … }, { code: 'FIB', … }, { code: 'LDH', … },   // 全 8 项都是化验 code
]
```
`intakeCard.js:587`：`REQUIRED_BASICS.filter((b) => !seenCodes.has(b.code))` —— 判据是"**这个 code 有没有出现过**"。

stage/subtype/诊断 属于 **`patient` 档案字段**，既不在 `REQUIRED_BASICS` 里，也不是 row code，**复用不了**。A2 要的是三态模型（§4）：`有值 / 有字段但空 / 根本没有字段`，而 `missingBasics` 只能表达第一态之外的二态之一。

**改法**：新增 `profileTriState`（或同等结构），与 `missingBasics` 并列输出、**不合并**（合并会把"没查这个化验"和"档案没填分期"混成一个告警，医生分不清）。

### P0-3 附页 owner 隔离（见 §6-1，含可执行判据）

### P0-4 标线候选清单必须有产物

计划 D 段 `:88` 写"审核 AI 产出一份候选标线清单…交用户/医生确认前不进代码"——方向对，但**清单本身没有落盘位置**。用户在触发语里原话："审核AI必须要理清楚，哪些情况能判断为高危、低危、中危？**将这些标线收集清楚**。就能知道需要哪些数据了。"⇒ 清单是**交付物**，不是审核者的口头答复。

**改法**：新建 `docs/问诊卡危险分层标线候选.md`（或同目录），内容骨架用 §3.2 的表，**每条必须带**：判据原文 / 出处（指南名+版本、或"项目已有合同"）/ 确定性（已定稿 / 待医生确认）/ 本项目能否自动判（有值 / 空 / 无字段）。并且**表头写死**："本表为候选，不构成判定标准；未经医生签字确认的条目不得进入代码。"

## 3. 攻击点 1：高/中/低危标线到底是什么

### 3.1 先回答"当前有没有分层判定"：**没有，一条都没有**

| 已有的东西 | 是什么 | 是不是"分层" |
|---|---|---|
| `CRITICAL_RULES`（`cardPolicy.mjs:49-88`，11 条） | 单次数值的**危急值报警**（WBC<1 或 >50、ANC<0.5、Hb<60、PLT<20 或 >1000、FIB<1、Lac≥4、IL-6≥1000、PT≥20、APTT≥60、K<2.8/>6、NT-proBNP≥1800） | **不是** |
| `P0_CODES` / `P1_DEMOTED_CODES` | "先看哪些项"的**展示优先级** | **不是** |
| `DISEASE_TAG_PATTERNS`（`cardPolicy.mjs:127+`） | 把名称/代码映射成**基因标签**（BCR::ABL1/TP53/KMT2A/IKZF1/MRD/染色体核型…） | **不是** |
| `missingBasics` | "这几个化验没出现"的提示 | **不是** |
| 任何 `risk` / `危险分层` / `高危判定` 函数 | — | **不存在**（grep 0 命中） |

**"危急值 = 高危分层"为什么不能画等号（三条区别 + 一个库里实锤）**：

| 维度 | 危急值 | 危险分层 |
|---|---|---|
| 时间尺度 | **单次**：一个时点的一个数 | **纵向**：跨多份报告的疗程级趋势 |
| 判定对象 | 单个 code 的阈值 | 多维度组合（遗传学 × MRD × 负荷 × 年龄…） |
| 用途 | 急诊处置（今天要不要升白/输板/查血气） | 方案选择与移植决策（要不要上 TKI/异基因移植） |
| **实锤** | WBC `0.71`（2026-08-05）命中"<1.0 危急"——**处置上必须报警**；但把它读成"疾病高危"就完全说反了，它是化疗后骨髓抑制 | 分层要的是"初诊 WBC 18.18（2026-07-21）"这类**基线**值，不是化疗中的谷值 |

### 3.2 逐维度：分层需要什么数据（**候选清单，不是判定标准**）

> **特别警示**：不同方案的切点互相冲突（尤其 WBC 阈值 30 / 50 / 100 各中心不同；COG/NCI 那套"年龄 1–9.99 岁 + WBC<50k 为标危"是**儿童**标准，**不能套到本例 30 岁成人身上**）。所以下表**只给"要看什么"，不给"多少算高危"**。

## 6. 攻击点 4：B 线打印附页的雷（计划只列了 1 条，我补 5 条）

### 6-1 **owner 隔离（P0-3）**：附页不能自己读 blob

已落地的事实（我实测）：

- `server.mjs:295-350`：`req.mbUser` + `authn.can/owns/ownsBlob` 已在钩子上生效；
- `server.mjs:1514-1545`（`/api/intake/card`）：**已按 viewer 过滤** ——`role!=='admin'` 只出本人 owner 的报告并 `loadPatientFor(viewer.id)`；admin 可用 `?owner=` 指定；
- `blob/:id`：非 admin 且 `!authn.ownsBlob(mbUser,id)` ⇒ 403。

⇒ **`?append=<id,id>` 若在服务端用内部 `getBlob(id)` 把字节拼进 html，就同时绕过上面两道**。而 id 由客户端提供，普通用户传别人的 report id 就能**越权拿到他人原件**（且 html 里是 base64，连 `blob/:id` 那道 403 都不会触发）。

**必须写死**：附页 id 解析**必须复用 `/api/intake/card` 现有的 owner 过滤**（即先按 viewer 过滤 `reports`，再只允许 `reports` 里的 id），**不是**另写一套；被拒 id 的行为要明写（建议：整单 403 并提示"含无权访问的报告"，**不要静默跳过**——静默跳过会让医生以为"没勾上"）。

**判据（进 `verify-auth.mjs`）**：普通用户 `GET /api/intake/card?append=<他人报告id>` ⇒ **403**；admin 用自己 `?owner=` 的 id ⇒ 200；普通用户 `append=<非本库id>` ⇒ 403。

### 6-2 **体积（P1-1，但要先定量）**

实测 `data/medbrief.db` blobs：**118 份、总 82 256 673 B、中位 378 176 B、最大 5 526 577 B**。base64 内嵌膨胀约 33%：

- 3 份中位数原件 ≈ **1.5 MB** → HTML ≈ 2 MB（可接受）；
- 3 份最坏 ≈ **16.5 MB** → HTML ≈ **22 MB**，`document.write` 进 iframe 极易卡死/白屏，打印也基本没法用。

⇒ 必须写上限 + 行为：建议**单份 ≤ 3 MB、合计 ≤ 8 MB（可调）**，超限**拒绝并明确提示"这份原件过大，未附；请单独打印"**，**绝不许静默降采样**（降采样 = 改原件，违反 B2 硬边界）。

### 6-3 **OCR 文本当"原件"（F3 的正面）**

现状 **98/98 份都有 blob**（`source` 分布：`image` 97 + 空 1），所以"没有原件"的路径今天不存在——**但它是历史存在的**（`source: 'text-only'` 在 `intakeCard.js` 注释里被明确提到过）。必须写死：**无 blob 的条目，附页位置显示"原件不可用"，绝不回退用 `report.text`**（`text` 是 OCR 抽取/重排结果，附出去就是把转录当原件）。判据：构造一条无 `sourceBlobs` 的副本库记录，附页渲染**不得**出现该记录的 `text` 片段。

### 6-4 **embed 模式下分页被关掉（计划完全没提）**

`lib/intakeCard.js:1353` / `:1360` / **`:1378`**：

```
.page2/.page3 { page-break-before: always }          // 正常打印
body.embed-preview .page2/.page3 { page-break-before: auto; margin-top: 14px }   // 打印预览弹窗里被改成 margin！
```

⇒ **打印预览（`embed=1`，`CardPage.jsx:119`）与新窗口纯净打印（`CardPage.jsx:67`）的分页行为不同**。附页若只在一条路径上验，"一报告一页"在另一条路径会变成"连续流"。
**判据**：两条路径各验一次 —— `?embed=1&append=…` 与不带 `embed` 的 `?append=…`，都要保证**每份原件前面有强制分页**（附页要自带 `page-break-before: always`，不要依赖 `.page2/.page3` 类名）。

### 6-5 **页数文案与"3 页"契约**

`CardPreview.jsx:61` 写死"打印预览（3 页 A4）"；`docs/问诊卡逻辑.md` 与 `verify-card` 也可能断言 3 页。附页后**总页数 ≠ 3 + 份数**（一份 CT 原件可能多页/一张图可能一页），所以文案必须**动态**且**不能按份数算**。F8 要同步的其实是三处：文案、`docs/问诊卡逻辑.md`、`verify-card.mjs` 里的页数断言。

### 6-6 **默认零变化怎么保证**

`?append` 缺省时必须是**逐字相同**，判据不能是"看起来没变"：取同一份 `card.html`（`mask=0` 与 `embed=1` 各一次），**改动前后 sha256 相等**。
