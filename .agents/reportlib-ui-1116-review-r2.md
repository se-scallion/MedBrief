## 二、5 个特别复核点

### ① 整行可点 + 行内删除图标 → 会不会冒泡同时开抽屉？

**会**（`Popconfirm` 的触发按钮在行内，click 会一路冒到行 `onClick`）。除了 `stopPropagation`，还有一个更隐蔽的坑：**行容器做成可点 div、里面再放按钮 = 嵌套交互元素**，屏幕阅读器会把整行读成按钮、里面的删除也读成按钮，语义冲突。
**修法（写进 D2 + 断言）**：
- 行点击**只挂在「主行类型文本」上的真实 `<button>`**（不要给整行 div 挂 `onClick`）；行容器只负责布局。
- 操作区统一 `<div onClick={(e) => e.stopPropagation()}>` 包一层（即使将来改成整行可点也安全）。
- 断言：`点删除图标 → 抽屉不打开`、`点查看/编辑/原件 → 抽屉不打开`、`点类型文本 → 抽屉打开`、`Tab 键可聚焦到删除按钮且 `aria-label="删除"``。

### ② 「按记录分页 + 组不跨页 + 跨页组头各出现一次」——**三条互斥，且今天的断言只是巧合**

v0.2 同时要求：**(a)** 按记录分页 `pageSize=20`、**(b)** 组不跨页拆半、**(c)** 跨页时同一天组头在每页各出现一次。`(a)+(b)` 在「某天份数正好压页边界」时必然要求改变页大小；`(c)` 只在**组被拆开**时才需要——与 `(b)` 直接矛盾。
我按真实数据跑了两种切法（证据见复跑命令）：
```
现状 66 份 / 28 组：方案A(按记录须可拆组) 4 页 [20,20,20,6]，同日跨页 0 次
                   方案B(不拆组)           4 页 [20,20,20,6]
合成「2026-10-16 再加 3 份」后：方案A → 4 页 [20,20,20,9]，**同日跨页 1 次**
```
即：**今天断言「4 页共 66」通过，纯属组边界正好落在 20/40/60**；明天多导一份就可能跨页，断言随即变红（或更糟：实现按 (a) 走、组被拆开，用户看到同一天出现两个组头 → 与「头部只写一次日期」的用户需求直接冲突）。
**单一裁决（P0）**：**按组分页**——每页固定 N 组（建议 8 组/页），组永不跨页，组头天然只出现一次；断言改为「页数 = ⌈28/N⌉、每页组数 ≤N、`Σ页内记录 = 66`、组头不重复」，**不再写死「4 页」**（那是数据快照）。若坚持按记录分页，则必须放弃 (b)(c) 中的一条，并把「同日续页」的组头文案写死（「2026-10-16（续）」）。

### ③ 「最多 2 标记」把「全文」挤掉 —— **这是在回退一条已经写下的教训**

`ReportsPanel.jsx:299-302` 的注释是 375 实测后写的原话：「不能显示成『—』——那会让『全文型』和『解析出 0 项』在手机上看不出区别，**家属/医生无从判断该不该点进去看原文**」。「全文型 + 推断 + 无原件」三标记同时命中时按 `推断 > 无原件 > 全文` 排序 → **恰好把「要不要点进去看原文」这个决策信号挤掉**。
**修法（P0-2′）**：不要用「标记数量」硬砍语义不同的三件事，而是**分层**：
- 主行：`检查类型`（ellipsis）+ `推断` 降级为类型末尾的小上标 `?`（项目里已有 `nameDirty ?` 的先例），不占 Tag 位；
- 次行：`无原件` 用图标 + `aria-label`（不占 Tag 位）+ `全文型` 保留为唯一 Tag。
断言：三标记同时命中时，「全文」仍在次行可见（或至少有 `aria-label`/`title` 可读），且次行不换行。

### ④ 搜医院命中但列表看不到医院 —— **保留匹配 + 补「为什么命中」**

`ReportsPanel.jsx:215-218`（**注意：输入里写的 `:230-238` 是列定义区，搜索谓词实际在 `:215-218`**）匹配 `id/hospital/reportType/kind/reportDate/barcode/patientName`。列表不显示医院后，搜「新桥」会命中但用户看不出原因。
**处置**：① 保留匹配（用户就是可能按医院找）；② **仅在 `kw` 命中非显示字段时**，次行临时追加一行「命中：医院 = 陆军军医大学新桥医院」（`kw` 为空不显示，避免常驻占位）；③ 占位符改成「搜类型 / 日期 / 医院 / 单号」（现在只写了前三个 + 报告号）。
断言：搜「新桥」→ 命中行出现「命中：医院…」；搜「血常规」→ 不出现该行（命中的是显示字段）。

### ⑤ 管理态与回收站 —— **回收站根本不该有管理态，用「不渲染」代替「切 tab 时重置」**

v0.2 用「切到 trash 自动退出管理态」实现，这依赖「记住在切 tab 时 reset」，一旦以后有人加第三个 tab 或改成路由跳转就会漏。
**更稳的做法**：`manage` 只在 `tab === 'active'` 时**渲染**（`{tab==='active' && <Segmented 浏览/管理/>}`），生效值用派生量 `const manageOn = manage && tab === 'active'`。这样「回收站里没有管理态」是结构上不可能出错，而不是靠回调补。
断言：`tab=trash` 时页面里 **0 个**「管理」控件、恢复/彻底删除恒可见（与 `manage` 无关）、`tab=active` 时删除按钮数在管理态前 0 / 后 = 当页份数。
