# 问诊资料卡 · 需求与设计（根本需求）

> 用户 2026-11-12 一句话定的根本需求：
> **「导入病友的病例、报告单，获得问诊（医生视角的）病况资料，用于给门诊医生快速了解病人情况。」**
>
> 三条硬边界（同一轮澄清）：
> 1. **数据只来自用户导入的文件**。不读 MedData 的任何库（`/api/summary`、`/api/state` 都不作为取数来源）。
> 2. **挂号是次要功能**：主鸿鹄在 114 没有号（用户确认），不做常驻扫描、不默认自动轮询。
> 3. **页面结构按功能权重排**，不是「一级页 ≤ 3」这种数量指标；屁大点功能不许占一级页面，能一页做完的不许拆两页。

---

## 一、医生在看什么（资料卡的取数与排序依据）

门诊血液科医生读一份外来资料，实际只做三件事：**是不是这个病 → 现在多重 → 下一步该看什么**。
所以资料卡的内容不是「把所有指标摊开」，而是按下面的优先级组织：

| 优先级 | 内容 | 为什么必须在这里 | 卡片呈现 |
|---|---|---|---|
| P0 | **疾病定性与残留病**：诊断全称（B-ALL 等）、分型/危险度、骨髓原始细胞 %、流式 MRD %、融合基因定量（如 BCR-ABL1）、染色体核型/关键突变 | 决定「是不是这个病、治疗有没有效」，没有这些医生无法判断阶段 | 首屏第一块，带日期与来源报告 |
| P0 | **异常项清单**：本次所有越出参考区间的项目（含箭头方向） | 医生先看红点，再决定翻哪张单子 | 一句话摘要 + 明细表（异常在前） |
| P1 | **血常规核心**：WBC、中性粒绝对值（感染风险）、Hb（贫血/输血指征）、PLT（出血风险）、网织红 | 化疗/维持期每次门诊必看；**正常值同样是信息**（说明骨髓抑制恢复了） | 表格，含参考区间与上次对比趋势 |
| P1 | **脏器功能与代谢**：ALT/AST、总胆红素、白蛋白、肌酐、尿酸、LDH | 决定化疗药能不能上、要不要减量；LDH 与肿瘤负荷相关 | 表格 |
| P1 | **炎症/感染**：CRP、PCT、ESR | 粒缺伴发热是血液科最常见急症入口 | 表格 + 是否在用抗生素（若有） |
| P2 | **凝血**：PT/APTT/FIB/D-二聚体 | 出血倾向、DIC 风险、置管前后 | 表格 |
| P2 | **铁代谢/营养**：铁蛋白、叶酸、B12 | 长期输血与营养状态 | 表格 |
| P2 | **免疫球蛋白 / 淋巴细胞亚群** | 免疫重建与感染风险 | 表格 |
| P3 | **其他项**（未归类的化验） | 兜底，避免漏 | 折叠 |

**缺项也要写出来**：卡片必须显式声明「WBC/Hb/PLT 未提供」，因为医生要区分「没查」和「你没给我」——
这两件事的临床后果完全不同（`summarizeForCard().missingBasics`）。

**红线（与 `.agents/testing-lessons.md` 的「不下结论」一致）**：
卡片只陈述数值、时间、趋势与出处；**不写诊断结论、不写治疗建议、不写预后判断**，也不做参考区间之外的「推断」。

## 二、资料卡结构（一页 A4，可直接打印给医生）

```
┌ 问诊资料卡 ─────────────────────────────── 生成时间 · 数据来源（本次导入 N 份报告）┐
│ ① 患者与诊断   姓名/性别/年龄 · 诊断全称 · 分型/危险度 · 起病时间 · 当前治疗阶段        │
│ ② 本次就诊诉求  主诉（由病友填）· 想问医生的问题（1–3 条）                             │
│ ③ 异常项摘要    共 N 项异常：①… ②… ③…（一行一条，带日期）                             │
│ ④ 疾病特异      骨髓原始细胞 / MRD / 融合基因 / 核型（各带报告日期与出处）              │
│ ⑤ 关键指标表    血常规 / 生化 / 炎症 / 凝血 / 铁代谢 / 免疫（异常在前，含参考区间与趋势） │
│ ⑥ 近期治疗与用药 化疗方案与周期、靶向药、输血、感染事件（有则列，无则写「未提供」）        │
│ ⑦ 缺失与声明    缺项清单 + 「本卡仅整理数值与趋势，不含诊断与治疗建议」+ 报告原件索引       │
└──────────────────────────────────────────────────────────────────────────────┘
```

## 三、导入管线（批量图片 → 可核对的结构化 → 资料卡）

```
批量选择/拖入图片（手机截图、拍照，可多张、可一次几十张）
  → ① 客户端预处理：按「同一张单子多张截图」分组 → canvas 纵向拼接成一张
  → ② 服务端识别：8008 `POST /api/ocr-vision`（macOS Vision，~10s）
                  降级：本地 8045 多模态视觉（gemini-3.5-flash-lite）；再不行人工粘贴文本
  → ③ 行解析：`parseLabRows()` → [{name, num, unit, refRange, flag, status}]（认不出的不瞎填）
  → ④ 查重（三层）：
         a. 图片精确重复：sha256(bytes)
         b. 图片近重复：dHash64 + 汉明距离 ≤ 6/64（同张单子拍两次）
         c. 报告内容重复：buildReportFingerprint(rows, meta)（行序无关、值变即变）
  → ⑤ 人工校正：识别结果以表格呈现，可改值/改单位/删错行（**必须有这一步**，OCR 不可能 100%）
  → ⑥ 入库：data/reports.json（一份报告一条：images[]、ocrText、rows、fingerprint、reportDate、hospital、kind）
  → ⑦ 生成资料卡：groupForDoctorCard + summarizeForCard → 渲染 A4 / 打印 / 导出 HTML
```

### 为什么拼接放客户端
- 手机截图原图就在浏览器里，`canvas` 拼接零上传、零依赖；
- 服务端拼接需要图像库（本机只有 `@napi-rs/canvas`，是 MedData 的依赖），跨项目耦合不值；
- 拼接后只上传一张，OCR 调用次数与耗时都降一半以上。

### 查重阈值
| 层 | 判据 | 命中动作 |
|---|---|---|
| 精确 | `sha256` 相同 | 直接拒绝入库，提示「这张图已导入过（报告 #id）」 |
| 近重复 | dHash 汉明距离 ≤ 6 | 提示「疑似重复」，让用户选「替换/保留两份」 |
| 内容 | 指纹相同 | 同上，但提示「同一份报告」（换了拍摄角度但内容相同） |

## 四、页面结构（按功能权重，不是按数量）

```
/（主页面）问诊资料卡
   ├─ 导入区：批量图片 / 拼接预览 / 识别进度 / 查重提示
   ├─ 校正区：识别结果表格（可编辑、可删行）
   └─ 资料卡：一页预览 + 打印 + 导出 HTML（就是给医生的东西）

/history（次要，可收进抽屉）  历史报告与指标时间线
/tools（次要，默认折叠）      挂号工具（114 登录 / 官网排班查询 / 预约记录）
                              —— **默认不自动扫描**，用户点了才查一次
```

判断标准（替代「一级页 ≤ 3」）：
1. 高频且直接产出交付物的功能 → 前台（资料卡）；
2. 低频工具 → 抽屉/二级入口，默认不自动运行；
3. 明显能一页做完的不许拆页：导入、校正、资料卡是同一条流程，必须在同一页完成。

---

## 五、验收标准（可复跑）

1. 批量导入 10 张截图 → 分组拼接正确、无丢图；重复导入同一张 → 被 sha256 拦住。
2. 同一张单子拍两次（轻微不同）→ 被 dHash 判为近重复并提示。
3. 一张化验单被拆成两张截图 → 拼接后一次 OCR 得到完整行集（不缺上下半）。
4. OCR 文本 → `parseLabRows` 结果与人工肉眼核对一致（认不出的行为空，不许编）。
5. 资料卡一页 A4 打印：异常项在血常规组内排第一；缺失项有显式声明；正文不含任何诊断/治疗措辞（断言见 `tests/verify-intake.mjs` 与速览红线）。
6. 报告入库后重开页面仍在（`data/reports.json` 持久化）。

## 六、暂不做（延后 + 触发条件）

| 项 | 触发条件 |
|---|---|
| 病理/骨穿报告字段级结构化（免疫组化、核型 ISCN 解析） | 出现「医生按字段筛选骨穿报告」的真实需求 |
| 指标趋势图（多报告时间轴） | 卡片用满一个迭代后，医生仍要求看图 |
| 多患者档案（一个病友一份卡） | 真的同时维护 ≥2 个病友 |
| 挂号自动化/常驻扫描 | 出现「在 114 有号的目标医生」（当前主鸿鹄无号，不做） |

# 附：工程实现（数据模型 / 链路 / 查重 / 分期 / 排雷）

## 二、数据模型（`data/intake/**`，全部 gitignore）

```
intake/<patientId>/
  patient.json                # 病友基本信息（姓名/性别/年龄/诊断/分型/阶段/来源与授权说明）
  batch-<batchId>/
    meta.json                 # 导入时间、来源设备、备注
    img/<imageId>.jpg         # 原图（保留原文件，不改写）
    img/<imageId>.json        # {sha256, w, h, groupId, stitchRole, source:"upload|stitch"}
    ocr/<imageId>.json        # 识别原文（blocks[] + 拼接文本 + 引擎与耗时）
  reports/<reportId>.json     # 一张检查单 = 一条 report（含类型、日期、医院、来源图、原文、结构化行）
  card.json / card.html       # 生成的资料卡（快照，可复现）
```

- `report.type`：`lab`（化验）/ `pathology`（病理/骨穿）/ `imaging`（影像）/ `discharge`（出院小结）/ `drug`（处方/用药）/ `unknown`
- `metric` 行：`{code, label, value, unit, refLow, refHigh, flag: high|low|normal|unknown, measuredAt, sourceImageId, rawSnippet}`
- **每条 metric 必须能回链到原图**（`sourceImageId` + `rawSnippet`），医生质疑时能当场翻图。

## 三、导入与识别链路

```
手机截图/相册（批量选择）
  → [可选] 两张半截图拼接（前端 canvas 纵向拼，产出新图 + 记 stitchRole）
  → 上传（base64 → 服务端落盘，算 SHA-256）
  → 查重 L1：sha256 命中 → 标 duplicate（不自动删，等人确认）
  → 识别：本机 8008 网关（macOS Vision 文本块）→ ocr/<id>.json
      └ 失败/超时 → 明确标「未识别」，允许人工补录（绝不静默留空）
  → 结构化：规则解析（项目/结果/参考区间/单位）+ AI 兜底 → 行级结果 + 每行置信度
  → 人工校对：低置信度行高亮；确认后才进 report
  → 出卡：card.html（A4 打印）+ card.json（可再次生成）
```

**为什么不用云端 OCR**：病友是**他人**的医疗与身份数据，默认只走本机 8008（`127.0.0.1`），不上传外网；
控制台 AI 也维持不授权（`console.yaml: ai.context_docs: []`）。

## 四、查重：宁可重复，不可丢

| 级别 | 判据 | 处置 |
|---|---|---|
| L1 文件级（**本期就做**） | 图片 SHA-256 完全一致 | 标 `duplicate`，默认不重复识别，人可强制继续 |
| L2 报告级（延后） | 报告日期 + 医院 + 类型 + 指标 code 集合指纹 | 提示「疑似与 X 重复」，**永不自动删除** |
| L3 行级（本期就做） | 同一 report 内 `code+value+unit` 完全相同 | 合并重复行并留痕 |

**判据**：任何情况下都不自动删用户资料；查重只做「标记 + 提示」。

## 七、排雷（本功能的 R/F，证据与取舍）

- **R1 需求前提**：用户原话明确「导入病友数据」，且明确「没有让你从 MedData 取数」→ 旧通道作废（不是优化，是改正）。
- **R2 8008 识别可用性**：`/api/ocr-vision` 实测存在（`MedData/server.mjs:2147`，入参 `{id, image:dataURL}`，阻塞约 10s，60s 兜底），但**对真实检查单的识别质量 `[未取证]`** —— P0 第一件事是拿 5 张真图跑通，跑不通就转人工为主。
- **R3 查重误判**：photo 重拍/裁剪后 sha256 必变 → 只做 L1 绝不误删；L2 需 OCR 文本相似度，误判成本高，延后。
- **R4 语义裂缝（拼图）**：一张单被切成两张 → 单张看是「半张」，行数不全。**必须人工确认分组**，不允许自动拼（拼错比不拼更危险）。
- **R5 隐私**：病友是他人医疗数据 → 本机处理、默认脱敏开关（姓名可打码）、导出包不含身份证/手机号。
- **R6 过度设计**：不建 OCR 模型、不做多医生、不做云端同步。
- **F1** 落盘目录 `data/intake/**` 必须进 `.gitignore`（含病友医疗数据，绝不能进版本库）。
- **F2** 资料卡导出含姓名 → 提供「脱敏打印」开关。
- **F3** 报告日期靠 OCR 识别，识别错会导致 L2 查重误判 → L2 一律人工确认。
- **F4** 识别失败必须显示「未识别」而不是空表，否则医生会以为「这项没做」。
- **F5** 测试用固定 fixture 图片 + 独立 `data/intake-test/`，不碰真实病友数据。
- **F7** 新增端点要重启 5174（谁改谁重启自验）。
- **F9** `data/intake/**` 由单一 owner 写（我），Bot 不写病友数据。

**取舍**：批量上传·L1 查重·识别原文·人工校对·资料卡打印 = **留（P0）**；结构化抽取 = 留（P1）；
拼图与分组·L2 查重 = 留（P2）；趋势图·病理精读 = 延后（触发：同一病友 ≥2 次同指标 / 医生要按字段筛报告）；
MedData 8787 取数入口 = **砍**（用户明确不需要）。

# 怎么用（家属视角，3 步出纸）

打开 `http://127.0.0.1:5174/`（默认就是「资料导入」页）。全程本机，图片不出网。

## 第 1 步 · 把图丢进去
- 手机截图最省事：**Ctrl/⌘+V 直接粘到页面上**（一次可粘多张），或拖拽/点选批量导入。
- 同一张检查单被拍成两张时：勾选这两张 → 点「拼接」，系统纵向拼成一张并保留原图回链。
- 已导入过的图会被标「疑似重复」，不会自动丢，由你决定。

## 第 2 步 · 逐张识别与校对（关键的一步）
- 点「识别」→ 等约 10 秒（本机 8008）→ 出原文与指标表。
- **黄底「低置信」行**：识别不确定，重点核对；**红底**：越出参考区间的异常项。
- 值、单位、参考区间都能直接改，行可以删。识别不出时页面会明确写「未识别」，可粘贴文本再解析。
- **「推定」标记**：名称是按标准序号补回来的（不是识别出来的），医生看卡时能分辨。

## 第 3 步 · 生成资料卡
- 填病友基本信息（不含身份证/手机号）+ 家属三问 →「生成资料卡」→ 预览 → 「打印 / 存 PDF」。
- 默认**姓名脱敏**（`王*`），给医生看时可按需关掉。
- 卡的一页结构：① 异常项（优先看）② 最新指标（每项最近一次）③ 关键趋势（关键 8 项）④ 家属三问。

## 已知边界（别指望它替你做判断）
- **数值识别 ≈100%，字段覆盖 ≈87%**（真实朝阳血常规实测 20/23；缺的 3 项是 OCR 没吐出结果值）。
- 合成单据 11/11、真实单据 20/23：**不同医院、不同单据类型（骨穿、出院小结、外院化验）未验证**，第一次遇到请按「校对」流程逐行看。
- 卡里**只陈述数值、日期、趋势与出处**，不写诊断结论与治疗建议；医生的判断不可替代。
- 病友是他人的医疗数据：只落本机 `data/intake/`、`data/reports.json`（均 gitignore），不进版本库、不上外网。
