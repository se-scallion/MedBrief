## 1. 七个阶段

| # | 阶段 | 实现 / 判据 |
|---|---|---|
| 1 | **发现** | 递归 ≤2 层；按**魔数**识别 jpg/png/gif/webp/**pdf**；跳过 `_t` 缩略图、<20KB、`07085632` 头的微信 V2 加密 `.dat` |
| 2 | **取数** | 图片 → `POST /api/intake/ocr`（8008，并发 6，缓存 `data/tmp/wf-ocr-cache.json`）；PDF → `tools/pdf-extract.py` 文本层（无文本层才栅格化 OCR） |
| 3 | **身份** | 单号：`报告单号/条码号/报告编号/检测条码/Barcode` → `MAX\d{6,}` → `V\d{11}`；日期：`报告时间/报告日期/送检日期/采集时间/接检时间`，兜底取正文最后一个日期并打 `dateFromFallback`；医院：`就诊医院/送检单位`；项目：`项目名称` |
| 4 | **判重（四层）** | ① `sha256` 字节级 ② **原件已在 `data/intake/**/archive`**（同一字节=导过）③ **库里已有同「单号+报告日期」** ④ 批内同「单号+**报告类型**+报告日期」（留字节更大者）。**不用 dHash 单独判重** |

> **客户端预检口径（2026-11-17，批量导入改造）**：录入页 `addFiles` 会先算**文件字节 sha256**（`crypto.subtle` 可用走原生，否则自写纯 JS —— 手机经局域网 http 打开时非安全上下文，`crypto.subtle` 必然 undefined），只做两件事：① **批内强比对**（同一批里同字节 ⇒ 不建第二张卡）；② **对库 exact**（库内已有同 sha256 ⇒ 仍建卡但打「同一文件已导入过」）。**dHash 永不预判**（同版式不同日期汉明距离 = 0，实测会把 14 张不同影像报告聚成一簇）。单据级（单号+日期+类型）判定仍只在入库时由服务端 `findDuplicate` 做，前端不得自成第二份判定。
| 5 | **行抽取** | 四列表 → `parseOcrTable()`（保留定性行：B型/未见/阴性）；两列表（融合基因）→ `parseTwoColumnTable()`；PDF 只出 1 行以内 → 判为误解析，改走全文型 |
| 6 | **跨屏配对** | 三条接受路径：① **血常规算术铁证** `白细胞计数 × 淋巴细胞百分比 ≈ 淋巴细胞计数`（分子分母可分布在两页）② 重叠 ≥2 行且 b 大多是 a 没有的行 ③ 页1 **末行** == 页2 **首行**；再**贪心独占分配**（一份页1 只配一份页2），配不上的进 `孤页/` |
| 7 | **分类 + 入库** | 化验单屏 / 影像全文（`textOnly`：rows=[]、全文进 `report.text`）/ 拼接 / 孤页 / **票据（拒收，不进报告库）**；入库时先 `POST /api/intake/blob` 存原件，再 `POST /api/intake/reports` 显式带 rows |

## 2. 判重口径（这四条缺一条就会出事）

| 层 | 键 | 实测为什么必须有 |
|---|---|---|
| ① | 文件 `sha256` | 同一文件被复制到两个目录（`RWTemp` 与 `Desktop/122` 各一份，字节完全相同） |
| ② | archive 里同字节 | 旧 CLI 已归档过的 PDF，再从目录扫一遍会重复导 |
| ③ | 单号 + 报告日期 | 库里有记录（别的会话导过），扫目录时不该再导；**同一送检批多份报告共用同一个条码**（融合基因 4 份都是 `V00000000000`），只按条码会互相误杀 |
| ④ | 批内 单号 + 报告类型 + 报告日期 | 同一页的两种导出（png 431KB / jpg 271KB）、重复截图（同单号同报告时间） |

**反例（已写进断言）**：`凝血 07-26` 与 `凝血 08-04` 的 dHash 汉明距离 = **0**，`findDuplicate()` 已加护栏——dHash 命中必须「同单号或同报告日期」才算重复，否则第二批新报告会被直接拒收。

## 3. 原件（Blob）——决定以后能不能重跑识别

- 表：`data/medbrief.db` 的 `blobs(id f_xxx, sha256, kind, type, size, width, height, origin_path, report_id, created_at, data BLOB)` + `blob_tombstones`（照 MedData，`node:sqlite` 内置，零依赖）
- 报告记录：`sourceBlobs: [{blobId, role, sha256}]`，`role = original | stitched`
- 取回：`GET /api/intake/blob/<id>`（实测 sha256 与源文件一致）；清单：`GET /api/intake/blobs`
- 原件同时复制到 `data/intake/<patient>/archive/<sha8>/`（兼容旧约定，也被判重第②层使用）

## 4. 已知边界

- 微信 `msg/attach` 里 `07085632` 头（V2）的图片**解不出**（单字节 XOR 与 AES-128-ECB 试探均失败）→ 必须让用户从微信「查看原图」导出，或落到 `temp/RWTemp/<月>`。
- **拼接图不能当数据源**：整图重跑 OCR 会丢行（实测丢 2 行/2 行）→ rows 用两页各自 OCR 的并集，拼接图只作完整原件。
- 影像/核型/mNGS 等全文型报告没有数值行，卡片只展示原文摘要，不进趋势段。
- 抬头被裁掉的孤页不猜日期，进 `孤页/` 等人工给日期。
- OCR 噪声（`⑦/◎`、`↑→个`、`μmol/L→wmol/L`、`10^9/L→10~9/L`）在解析器清洗，每行留 `rawSnippet` 可回溯。

## 6. 类型口径与人工纠错（2026-11-14）

- **两个字段分工**：`kind` 是**粗枚举**（`lab | pathology | imaging | discharge | drug | unknown`，前端 KIND_OPTIONS 与 MedData 的 records/docs 分流都依赖它，**不要改成细类**）；`reportType` 是**人类可读细类**（`超声-床旁`、`CT-胸部`、`磁共振-头颈`、`凝血四项`、`融合基因`、`病原mNGS`…）。
- **报告列表「类型栏」显示 `reportType`**，为空才回退 `kind` 的 label（`web/src/pages/intake/ReportsPanel.jsx`）。
- 类型命名统一在工作流 `normalizeType()` 里（超声-床旁超声→超声-床旁、心电图-普通心电→心电图、CT类血管增强→CT-血管增强、融合基因（定性/筛查）→融合基因…），入库即一致。
- **纠错走 MCP**：`intake_update_report({ reportId, reportType?, kind?, hospital?, reportDate?, rows? })` → `POST /api/intake/reports/<id>/patch`，每次改动落 `patchLog`（可审计），不提供删除。
